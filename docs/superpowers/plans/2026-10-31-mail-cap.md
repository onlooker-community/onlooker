# Mail Cap Per Recipient Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cap mail per recipient address for each kind of mail (reset, verify, invite), and cap all mail at 80 per UTC day. The cap is checked before any token is retired, so a refused request leaves the recipient's current link working.

**Architecture:** A D1 table `mail_sends` holds fixed-window counters, keyed by kind plus a hash of the address, and one global row per UTC date. `claimMailSend` in `apps/api/src/db/mail-sends.ts` bumps each counter in a single upsert. Each of the three sending handlers calls it before its token work. `apps/api/src/email/cap.ts` turns a refusal into a 429 and reports the global ceiling to Sentry. The five-minute cron prunes old rows. A source guard keeps every future sender claiming first. The web client stops waiting out long `Retry-After` values.

**Tech Stack:** Cloudflare Workers, D1 with drizzle-kit migrations, vitest with `@cloudflare/vitest-pool-workers` (apps/api), vitest with jsdom (apps/web), and bash source guards.

**Spec:** `docs/superpowers/specs/2026-10-31-mail-cap-design.md`. Linear ONL-222.

## Global Constraints

- Limits: `reset` 3 per hour per address, `verify` 3 per hour per address, `invite` 3 per day per address across all orgs, all mail 80 per UTC day.
- Address key: `loginAttemptKey(address)` (trim, lowercase, sha256) prefixed by kind. Never store a plaintext address.
- forgot-password answers `200 { success: true }` when refused, byte-identical to a send. resend-verification and invites answer `429`, code `rate_limit_exceeded`, with `Retry-After` in whole seconds rounded up, minimum 1.
- A refusal at the global ceiling calls `monitor.captureException`. A per-address refusal does not.
- Every claim runs before `deleteVerificationTokens` / `deletePendingInvitesFor` / `sendEmail` in its handler.
- `@cloudflare/vitest-pool-workers` does not apply `vi.mock`. Anything that must observe a call rather than a result is a source guard or an injected dependency.
- Edit tracked files with the Edit/Write tools, not `sed -i` or heredocs (CLAUDE.md, "Edit tracked files with the file tools").
- Commit through `/git-workflow:commit`. American English everywhere.
- Run one test file as `pnpm --filter @onlooker/api test mail-sends`, with **no `--`**. `test -- name` runs the whole suite.

```ts
 * Mail sent per recipient, in fixed windows, for the mail cap (ONL-222).
```

```ts
import type { D1Database } from "@cloudflare/workers-types";
import { loginAttemptKey } from "./login-attempts.js";

/**
 * The mail cap: per recipient for each kind of mail, and per day for all of it.
 *
 * The whole policy and its statements live here. See
 * docs/superpowers/specs/2026-10-31-mail-cap-design.md for why the counters
 * are per kind, and why each handler claims before it touches a token rather
 * than sendEmail claiming on its way out.
 */

export type MailKind = "reset" | "verify" | "invite";

const HOUR_MS = 60 * 60_000;
const DAY_MS = 24 * HOUR_MS;

/** Sends allowed to one address per window, by kind. */
export const MAIL_LIMITS: Record<MailKind, { max: number; windowMs: number }> = {
	reset: { max: 3, windowMs: HOUR_MS },
	verify: { max: 3, windowMs: HOUR_MS },
	invite: { max: 3, windowMs: DAY_MS },
};

/**
 * All mail, per UTC day. Resend's free tier allows 100 a day and 3,000 a
 * month; 80 leaves headroom under the first, and 80 x 31 = 2,480 keeps under
 * the second without a counter of its own.
 */
export const DAILY_MAIL_CEILING = 80;

/** Longer than the longest window, so a prune never forgets a live count. */
const RETENTION_MS = 2 * DAY_MS;

export type MailClaim =
	| { ok: true }
	| { ok: false; scope: "address" | "global"; retryAfterMs: number };

/** The day's ceiling row. A new UTC date is a new key, so it never needs resetting. */
export function globalMailKey(now: Date): string {
	return `global:${now.toISOString().slice(0, 10)}`;
}

/**
 * Count one send against `key` and answer the count and the window it landed
 * in.
 *
 * One statement, for the reason recordLoginFailure is one: a read followed by
 * a write lets two concurrent requests each see the old count and land as one.
 * SQLite evaluates every SET expression against the row as it was, so both
 * CASEs read the old window_start.
 */
async function countSend(
	db: D1Database,
	key: string,
	windowMs: number,
	now: Date,
): Promise<{ count: number; window_start: string }> {
	const ended = new Date(now.getTime() - windowMs).toISOString();

	const row = await db
		.prepare(
			`INSERT INTO mail_sends (key, window_start, count)
			 VALUES (?, ?, 1)
			 ON CONFLICT(key) DO UPDATE SET
			   count = CASE WHEN mail_sends.window_start <= ?
			                THEN 1 ELSE mail_sends.count + 1 END,
			   window_start = CASE WHEN mail_sends.window_start <= ?
			                       THEN excluded.window_start ELSE mail_sends.window_start END
			 RETURNING count, window_start`,
		)
		.bind(key, now.toISOString(), ended, ended)
		.first<{ count: number; window_start: string }>();

	if (!row) throw new Error("mail_sends: the upsert returned no row");
	return row;
}

function msUntilNextUtcMidnight(now: Date): number {
	const next = Date.UTC(
		now.getUTCFullYear(),
		now.getUTCMonth(),
		now.getUTCDate() + 1,
	);
	return next - now.getTime();
}

/**
 * Claim one send of `kind` to `address`, or answer why not.
 *
 * The address is claimed first, and a refusal there stops before the global
 * row: one bombed address must not spend the day's ceiling for everybody.
 * A claim counts even if the send then fails, so a Resend outage cannot be
 * retried into a burst.
 */
export async function claimMailSend(
	db: D1Database,
	kind: MailKind,
	address: string,
	now: Date = new Date(),
): Promise<MailClaim> {
	const limit = MAIL_LIMITS[kind];
	const mine = await countSend(
		db,
		`${kind}:${await loginAttemptKey(address)}`,
		limit.windowMs,
		now,
	);
	if (mine.count > limit.max) {
		return {
			ok: false,
			scope: "address",
			retryAfterMs:
				new Date(mine.window_start).getTime() + limit.windowMs - now.getTime(),
		};
	}

	const all = await countSend(db, globalMailKey(now), DAY_MS, now);
	if (all.count > DAILY_MAIL_CEILING) {
		return {
			ok: false,
			scope: "global",
			retryAfterMs: msUntilNextUtcMidnight(now),
		};
	}

	return { ok: true };
}

/** Drop counters old enough that no window could still be open; answer how many. */
export async function pruneMailSends(
	db: D1Database,
	now: Date = new Date(),
): Promise<number> {
	const cutoff = new Date(now.getTime() - RETENTION_MS).toISOString();

	const result = await db
		.prepare("DELETE FROM mail_sends WHERE window_start < ?")
		.bind(cutoff)
		.run();

	return result.meta.changes;
}
```

```ts
import {
	DAILY_MAIL_CEILING,
	type MailClaim,
	type MailKind,
} from "../db/mail-sends.js";
import { monitor } from "../monitoring";
import { ApiError } from "../types";

/**
 * What a handler does with a refused mail claim.
 *
 * Separate from db/mail-sends.ts so the counting stays free of Sentry and
 * HTTP, and with its dependencies injectable because the Workers pool cannot
 * mock modules - the shape runScheduled's ScheduledDeps already has.
 */

export type MailRefusal = Extract<MailClaim, { ok: false }>;

export type MailCapDeps = {
	monitor: Pick<typeof monitor, "captureException">;
	log: (line: string) => void;
};

const realDeps: MailCapDeps = {
	monitor,
	log: (line) => console.log(line),
};

/**
 * Log the refusal, and raise an issue if it was the day's ceiling.
 *
 * Only the ceiling pages anybody. A capped address is the cap working; the
 * ceiling means legitimate mail is being refused until UTC midnight - possibly
 * because someone holding many valid addresses is driving forgot-password -
 * and without this it would first surface as Resend refusing to send.
 *
 * The line names the kind and never the address.
 */
export function reportMailRefusal(
	refusal: MailRefusal,
	kind: MailKind,
	deps: MailCapDeps = realDeps,
): void {
	const global = refusal.scope === "global";
	deps.log(
		JSON.stringify({
			event: global ? "mail_global_ceiling" : "mail_address_capped",
			kind,
		}),
	);
	if (global) {
		deps.monitor.captureException(
			new Error(
				`mail: the daily ceiling of ${DAILY_MAIL_CEILING} sends is spent; refusing ${kind} mail until UTC midnight`,
			),
			{ tags: { kind: "mail_global_ceiling" } },
		);
	}
}

/**
 * The 429 for a caller who may be told: the same code and Retry-After the
 * login backoff answers. forgot-password never throws this - its refusal must
 * look exactly like a send.
 */
export function mailRateLimitError(refusal: MailRefusal): ApiError {
	return new ApiError(
		429,
		"rate_limit_exceeded",
		refusal.scope === "global"
			? "Too many emails are being sent right now. Try again later."
			: "Too many emails to this address. Try again later.",
		undefined,
		{
			"Retry-After": String(Math.max(1, Math.ceil(refusal.retryAfterMs / 1000))),
		},
	);
}
```

```bash
		function finish() {
			if (fn != "" && send) {
				senders++
				if (!claim || send < claim || (del && del < claim)) bad = bad " " fn
			}
		}
		FNR == 1 { finish(); fn = "" }
```

# Librarian Write Denominator Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `onlooker doctor`'s write denominator for librarian count scans that
actually reached classification, instead of counting every session in which any
librarian hook fired.

**Architecture:** Librarian already emits `librarian.scan.complete` on all three
of its terminal paths, but stamps two of them `outcome: "empty"` — the bail that
never had a chance to write, and the full scan that had one and declined. Task 1
and Task 2 separate those in the emitter, reusing the `skipped` / `skip_reason`
vocabulary the schema already defines and librarian never uses. Tasks 3 and 4
then let a `STREAMS` entry name the events that count as a chance to write, and
build the opportunity narrowing from those events rather than from hook firings.

**Tech Stack:** JSON Schema + TypeScript (`schema`), Bash + bats (`ecosystem`),
TypeScript + vitest (`onlooker`).

**Spec:** `docs/superpowers/specs/2026-09-06-librarian-write-denominator-design.md`

## Global Constraints

- Three repositories, in order: `schema`, then `ecosystem`, then `onlooker`.
  Tasks 1 and 2 each need the previous one **released**, not merely merged.
- Tasks 3 and 4 are in `onlooker` and do **not** depend on Tasks 1 and 2 landing.
  See "Ordering" below.
- American English in commits, comments, identifiers, and docs.
- Edit tracked files with the `Edit`/`Write` tools, never `sed -i` or a heredoc.
  The `lineage` and `inspector` plugins hook on tool calls, not on filesystem
  changes, so a shell edit is invisible to the ledger.
- Every commit goes through the `/commit` skill. Never `git commit -m` ad hoc.
- All work lands via a branch and a PR. Never push to `main`, in any of the
  three repositories.
- TDD: write the failing test, watch it fail for the right reason, then
  implement.

## Ordering

Tasks 1 and 2 are a chain: the schema must allow `skip_reason:
"no_new_artifacts"` before librarian may emit it, and the schema package must be
released before `ecosystem` can depend on the new value.

Tasks 3 and 4 are independent of that chain and can land at any time. The rule
they implement counts `outcome` in `{ok, empty}`, which is correct after Task 2
and merely over-counts slightly before it — and cannot over-count at all today,
because librarian emits nothing on this machine (`onlooker-ujtf`).

**Do not block Tasks 3 and 4 on Tasks 1 and 2.**

- [ ] **Step 3: Add the field and the option**

In `eventlog.ts`, add to the `EventScan` interface, beside `sessionStarts`:

```typescript
	/**
	 * Sessions in which an event occurred that means the entry had a real
	 * chance to write, keyed by the criterion's `key`.
	 *
	 * A hook firing is the wrong denominator for a plugin whose write path
	 * sits behind bails: `librarian-session-end` fires every session and
	 * usually exits before classification starts, so counting its firings
	 * charges librarian for chances it never had. The plugin's own
	 * `scan.complete` says which sessions actually reached the write path.
	 *
	 * Every requested key is present. An empty list means "asked, and
	 * nothing matched", which is a different claim from an absent key.
	 */
	sessionsByWriteChance: Record<string, string[]>;
```

Add to `scanEvents`'s options:

```typescript
	/**
	 * Event criteria that mark a real chance to write, supplied by the
	 * caller from `STREAMS`. `outcomeIn` is a positive set: an `outcome`
	 * this list does not name is not counted, so a value added to the
	 * emitter later is excluded by default rather than silently counted.
	 */
	writeChances?: ReadonlyArray<{
		key: string;
		type: string;
		outcomeIn: readonly string[];
	}>;
```

Initialize it in the `scan` literal, next to `lastByPrefix`. The keys come from
`STREAMS` rather than from the log, so prototype collision is not reachable
here, but use the same construction as its neighbors for consistency:

```typescript
		sessionsByWriteChance: Object.create(null) as Record<string, string[]>,
```

Immediately after that literal, seed every requested key so an unmatched
criterion still reports `[]`:

```typescript
	// Seeded up front rather than on first match, so a criterion that
	// matched nothing is reported as an empty list rather than as an absent
	// key. `computeVerdict` reads an empty set as "exactly no sessions",
	// and that is the correct reading of "this plugin had no chance to
	// write" - an absent key would instead look like no narrowing at all.
	const chanceSessions = new Map<string, Set<string>>();
	for (const criterion of opts.writeChances ?? []) {
		chanceSessions.set(criterion.key, new Set());
	}
```

In `processLine`, after `payload` and `session` are established and after the
existing guard that drops records with no session, add:

```typescript
		for (const criterion of opts.writeChances ?? []) {
			if (type !== criterion.type) continue;
			if (typeof payload.outcome !== "string") continue;
			if (!criterion.outcomeIn.includes(payload.outcome)) continue;
			chanceSessions.get(criterion.key)?.add(session);
		}
```

Before `scanEvents` returns, materialize the map onto the scan, sorted so two
runs over the same log cannot disagree:

```typescript
	for (const [key, sessions] of chanceSessions) {
		scan.sessionsByWriteChance[key] = [...sessions].sort();
	}
```

```typescript

	// instead of by its hooks. See `StreamEntry.writeChances` for why a

	const triggeredIn = new Set<string>();

			triggeredIn.add(session);
		}

			for (const session of hooks.sessionsByHook[hook] ?? []) {
				triggeredIn.add(session);
			}
		}
	}
```
